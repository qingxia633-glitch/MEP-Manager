# Multi-source QuantityBuildPlan 0.4

**Contract.** An opt-in plan for a bounded, non-branching path of straight native WCS segments (mm) and reviewed RoutePath v1 crossing gaps. The plan contains the original projection, its digest, scope, engineering approval reference, material and measurement basis, and an explicit inventory of physical and material-specific events. Eligibility accepts the plan as an object in the existing evidence bundle. The Builder CLI consumes it in build and replay modes. Signals from the older single-edge contracts keep their existing semantics.

**Invariant.** Builder recalculates every length from WCS at RoutePath's 48 significant digits for square roots. Subsequent Decimal operations are exact or rejected. A native source and a gap contribute once per material item in either traversal direction. The audit shows physical metres, conduit metres, grouped wire metres and conductor metres. Only one wire basis can be issued for the same installation. Procurement remains a separate, unevaluated decision.

**Failure.** Every execution independently looks for the plan's exact digest and engineering approval digest in an operator-provisioned, read-only project grant outside the checkout. Only an administrator may provision this directory. The CLI has no trust-store option. An installation without that independent authority produces diagnostic planar values only. Missing height, transition, beam, allowance or installation evidence blocks issue. Explicit zero needs its own reviewed source. Unknown inputs never become zero.

**Acceptance.** Synthetic examples independently authorize a complete plan, replay its nodes, exercise ownership/units, corrupt identity, mutate geometry or change the approval, and call Builder directly. Project replay uses the verified original RoutePath sources and preserves null final quantities. Historical single-source outputs and the frozen Golden are checked separately.

## Input and execution

Use `quantity-eligibility/resolve.py --input bundle.json --output decision.json` with the plan in `objects[]`. An eligible decision exposes `quantity_formula_plan`. The Python exporter `multi_source.export_plan(plan)` independently rechecks eligibility. Use `design-net-quantity/resolve.py build plan.json --registry registry.json --output result.json` or `replay_validate plan.json --frozen quantity.json --output replay.json`. Replay compares the complete reconstructed quantity including the node evidence. Build reads the explicit registry and returns an object to the caller.

| Plan field | Required evidence |
|---|---|
| `schema_version`, `scope` | `0.4`; project, drawing and instance, DWG and report SHA-256, space |
| `route`, `route_sha256` | Qualified RoutePath v1 projection and canonical JSON digest. Each straight native length is measured from its two WCS vertices. A gap has both scoped parents, endpoint sides, WCS points, a separate crossing witness, reviewed unit conversion and review provenance. Repeated consistent traversals share the same component. |
| `approval`, `role`, `installation` | Project approval ID and byte SHA-256, local approved role, installation method, status and source. An outstanding material substitution or location issue keeps installation pending. |
| `material` | Wire and conduit specifications, positive integer group and conductor counts, positive exact cross-section in mm², and one issue basis from `conduit`, `grouped_wire`, `conductor`. |
| `events[]` | Each event names its physical ID, kind (vertical, beam, reserve or other), affected targets (physical, conduit, wire), status and source. A reviewed vertical leg supplies two WCS points in mm. An approved allowance supplies its net increment in m, including explicit zero. Pending events carry no numeric length. At least vertical, beam and reserve must be accounted for. |

The supported adjustment allocation is `per_route_before_counts`. A wire allowance in this basis is added before group and conductor multiplication. An allowance supplied only as an aggregate across conductors needs separate review of its basis. A pending wire-only event leaves an independently qualified conduit item measurable. The registry rejects an overlapping second wire item even if it uses a different basis. Mixed same-project legacy ownership requires reconciliation before issue.

## Execution authority

The operator provisions `C:\Program Files\MEP-Manager\quantity-grants` on Windows or `/etc/mep-manager/quantity-grants` on POSIX. Deployment must restrict writes to the independent approving authority. Record lookup uses the canonical plan SHA-256 as the filename, with a `.json` suffix. The grant binds that digest, scope, role, original approval ID and byte digest, review source, reporting precision and `approved_for_design_net` status. Store the original approved bytes in `approvals/<byte-digest>.json`. The receipt contains a reviewed semantic Gate per full native identity digest. Execution verifies each Gate, approved binding and accepted evidence strength with the existing admission contracts. Changing a material basis or source requires review of that plan. No project receipt is provisioned by this feature.

The exact value is preserved. The independent reporting policy supplies decimal places and half-even rounding for display. Node sources contain coordinates or reviewed references, including event ownership and units. The original plan plus its digest, the audit nodes and the operator receipt support replay. Procurement quantity remains null.

### Authority and ownership checks

The installed code fixes the authority root. Neither a request, a CLI option nor an environment variable selects it. Grant filenames use the canonical plan digest. Approval filenames use the validated SHA-256. Reads check each ancestor with lstat, reject symbolic links and Windows reparse points (including junctions), require a regular single-link file, and check the opened file identity. Eligibility, direct build and replay perform these checks independently.

Deployment must protect the executable, Python loading environment, parent directories, grants and approval originals. The requesting account must lack permission to write, rename, replace, create links or change access controls there. Only the independent approving authority may publish reviewed bytes and receipts. The application does not audit the full OS ACL, identify the submitting person or cryptographically authenticate a human signature. An operator must verify those permission boundaries under the actual service and applicant accounts before enabling issue.

Within one item, straight segments with positive collinear overlap are rejected, including a return along part of a parent and partially overlapping vertical legs assigned to the same material. Contact at a shared endpoint is allowed. A grant must reconcile each positive event in `event_allocations`, keyed by event ID, with its source, stable `physical_component_id` and basis (`vertical_path` or `net_additional_to_measured_path`). The reviewer establishes that a scalar is an additional increment over measured geometry and other events. An unreconciled positive extent blocks issue. Reusing a physical component for the same owner blocks issue even under another event label.

Within a common drawing snapshot, registry checks compare component identities, actual WCS extents and event ownership. To allocate the same route to two independently approved installations of one material family, each plan supplies its stable `material.item_id` and the independent receipt must bind that ID as `material_item_id`. The approving authority assigns one ID to a physical installation across reporting bases. Changing specifications, labels or the group/core reporting basis alone gives no second entitlement. Without reviewed distinct identities, uncertain shared coverage requires reconciliation. Legacy records without enough ownership evidence still require same-project reconciliation.
